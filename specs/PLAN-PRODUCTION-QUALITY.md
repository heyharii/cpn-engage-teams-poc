# Production Quality Plan — Architecture, Features, UI/UX, Distribution

Status: PLAN (July 2026). Source of truth for taking CPN Engage from demo-POC
quality to distributable product quality. Written after a full code audit of
all three surfaces + both services.

## The honest verdict

What we have is a **demo skeleton with real plumbing in 3 places** (scores,
modules, feed posts) and **demo fakery everywhere else**. The three headline
problems:

1. **Architecture is not correct** — one global in-memory `state` object
   (cloned from `demoBootstrap`) is served to every user. Two employees
   opening the Profile tab see the *same* passport, streak, stats, and
   notifications. Only the point score is truly per-user. Nothing except
   scores/modules/feed survives a restart.
2. **Security is not correct for distribution** — admin content CRUD, demo
   reset, broadcast push, and directory read are all callable by anyone who
   can reach the URL. `PUSH_TOKEN` is optional and unset; API CORS is
   `origin: true`. Fine on a laptop, not fine on a client's network.
3. **UI/UX is below standard** — Feeds is a single flat list with emoji
   buttons (no composer, no comments, no images, no pagination); the employee
   app is a static dashboard describing demo data; admin (after the July
   pass) is the closest to acceptable but still has no auth, no system
   visibility, and no analytics.

Everything below is sequenced so that **architecture is fixed first** —
polishing UI on top of shared-global-state would be wasted work.

## Phase 0 — Architecture correctness (the spine) — ~1 week

Goal: every piece of data a user sees is either (a) truly theirs, or (b)
truly shared org data — and both survive restart. All writes are authorized.

### 0.1 Identity spine
- Every request from the tabs carries the Teams SSO token (already works on
  Profile); `/api/*` endpoints verify it and derive `oid` server-side.
- Browser/dev fallback: signed guest id, clearly labeled `verified: false`.
- Kill `state.currentUser` ("Narin") as an identity source everywhere.

### 0.2 Per-user state in Postgres (replaces the global `state` object)
New tables (api service):
- `user_profiles` (oid PK, name, email, department, joined_at) — upserted on
  first verified request; enriched from the bot directory.
- `user_module_progress` (oid, module_id, status, completed_at) — replaces
  `passport.modulesCompleted` fiction; drives per-user completion %.
- `user_challenge_runs` (oid, drop_id, answered_at, correct, points).
- Streaks computed from `score_events` timestamps (already exist) — no new
  writes needed.
- `/api/bootstrap` becomes `/api/bootstrap?me=` → assembled per user:
  `{ me: {profile, score, streak, progress}, org: {modules, dailyDrop, feed} }`.
  The shared demo object remains ONLY as first-run seed content.

### 0.3 Authorization
- `/api/admin/*` and bot `/internal/*`: require `x-admin-key` (server-side
  env `ADMIN_KEY`, per-install random — generated by the installer, shown
  once). Admin console stores it after a simple key-entry screen (localStorage).
- Make `PUSH_TOKEN` mandatory in production compose (fail fast at boot if
  unset when `NODE_ENV=production`).
- CORS: exact-origin allowlist from env (`ALLOWED_ORIGINS`), no `origin: true`.
- Reactions/feed writes: require SSO token (or guest id in dev mode).

### 0.4 Persistence completeness
- Move per-user reaction tracking fully to Postgres (drop the in-memory
  `reactionUsers` Map path; `toggleReactionDb` becomes the only path).
- Notifications list → table (append on events, per-user read cursor).
- Add `schema_migrations` table + numbered migration files instead of
  scattered `create table if not exists` (needed for on-prem upgrades).

Acceptance: two different Teams users see different profiles/progress; all
data survives `docker compose restart`; admin endpoints 401 without key.

## Phase 1 — Feeds to Facebook standard — ~1.5 weeks

The bar: a user lands on Feeds and it *behaves like a social feed*, not a
report. Reference mental model: Facebook group feed.

### Missing today → build
| Facebook-standard element | Today | Build |
|---|---|---|
| **Composer at top** ("Recognise someone…") | ❌ only via bot chat | Inline composer card: pick colleague (people-picker from directory), pick Belief chip, write message, optional photo. Posts to the same feed pipeline as the bot. |
| **Comments** | ❌ none | `feed_comments` table (id, feed_id, oid, author, body, created_at). Collapsed "View 3 comments" → expand thread + inline comment box. |
| **Reactions like FB** | 5 emoji buttons always visible | Single Like button + hold/hover → reaction picker (👍🎉❤️👏🔥); show top-3 reaction summary + count ("👍❤️ 12"); "you and 11 others". |
| **Author avatars** | initials circle | Initials stay as fallback; pull photo from Graph (`/photo/$value`) when tenant allows, cached server-side. |
| **Post types** | recognition only | recognition, admin announcement (pinned, distinct style), milestone auto-posts ("🎉 Narin completed Customer Empathy"), leaderboard weekly summary card. |
| **Infinite scroll + pagination** | full list in one fetch | `/api/feed?cursor=` keyset pagination (25/page), IntersectionObserver load-more. |
| **New-posts indicator** | manual Refresh button | 30s poll → "New posts ↑" pill (SSE later if warranted). |
| **Empty/loading states** | plain text | skeleton cards + friendly empty state with CTA to recognise someone. |
| **Relative times that update** | static on render | tick every minute. |

### Explicitly out (keep scope honest)
Shares, DMs, algorithmic ranking, video upload — not in this phase.

Acceptance: a user can post a recognition with a photo from the Feeds tab,
comment on someone else's post, react FB-style, and scroll a paginated feed
that updates itself.

## Phase 2 — Admin to "better standard" — ~1 week

The bar: a client admin runs their engagement program *without us on a call*.

### 2.1 Missing features
- **Announcements**: compose → posts pinned to Feeds + optional broadcast
  card to Teams (reuses push pipeline). Today admins literally cannot speak
  to the feed.
- **Daily-drop management**: the daily challenge is hardcoded demo content —
  admin must be able to author drops (question, options, points, schedule
  date) and see which drop is live. This is a **content gap worse than
  modules** (modules are editable, drops are not).
- **Scheduling**: pick send time for broadcasts/drops (pg-boss already
  installed — currently only used for the 30s test). Calendar-ish list of
  scheduled sends with cancel.
- **Recognition moderation**: hide/delete an inappropriate feed post
  (soft-delete flag; audit who hid it).
- **Analytics that answer the client's question** ("is engagement working?"):
  - participation over time (DAU on drops, module completions/week)
  - department league table
  - recognition graph volume (given/received by department)
  - broadcast delivery/read stats (delivered count already returned; store it)
- **System page** (see Phase 4 — surfaces the debug bundle in the UI).

### 2.2 UX corrections
- Login gate (the `ADMIN_KEY` screen from Phase 0.3) — right now the console
  pretends to be private but is public.
- Broadcast history ("what did we send, when, to how many") — table under the
  composer, from a new `broadcasts` table.
- Delete module: replace `confirm()` browser popup with proper dialog.
- Overview page becomes the analytics dashboard (stats today are static
  counts, not trends).

Acceptance: an admin can run a full week (author drop, schedule it, announce
a campaign, moderate a post, read the participation chart) with zero CLI.

## Phase 3 — Employee app to "personal truth" — ~0.5 week

The bar: everything on the Profile tab is *that user's real data* (enabled by
Phase 0.2 — this phase is mostly wiring UI to the new per-user bootstrap).

- Passport = real completion (their `user_module_progress` / total live
  modules), real streak (from score_events), real recent entries (their own
  events, not the shared demo list).
- Beliefs progress = their per-Belief points split (score_events has the
  data; add `belief` column to events at write time in the bot flows).
- "Today's drop" banner reflects whether *they* answered today, not the
  global demo status.
- Learning tab: modules carry per-user done/todo state + "continue in chat"
  deep link (`https://teams.microsoft.com/l/chat/0/0?users=<botId>`).
- Remove all remaining `demoBootstrap`-only widgets that cannot be made true
  (or clearly badge them "sample" until their phase lands).

Acceptance: two users' Profile tabs differ and match what they actually did.

## Phase 4 — On-prem distribution + post-distribution debugging — ~1 week

Goal: hand the client's IT ONE artifact + ONE runbook page; when something
breaks, they send us ONE file and we can diagnose without SSH access.

### 4.1 Distribution package
- `install/` directory in-repo: `docker-compose.prod.yml` (pinned image tags,
  restart policies, healthchecks, log rotation via `logging:` options,
  Postgres volume + nightly `pg_dump` sidecar keeping 7 days) +
  `install.sh` (checks docker, generates `.env` with random `ADMIN_KEY` /
  `PUSH_TOKEN` / DB password, prints the admin key ONCE, `compose up`).
- Publish versioned images to GHCR on git tag (CI job) — client updates =
  `install.sh --update vX.Y.Z` (pull + migrate + restart). No git on client
  boxes.
- `VERSION` baked into images at build; every service exposes `/version`
  (git sha + tag + build date).

### 4.2 Debuggability after hand-off
- **Structured logs**: pino JSON everywhere (api already Fastify/pino; bring
  bot's console.log to pino) with request ids; propagate `x-request-id` from
  tabs so a user report ("it failed at 14:32") is greppable.
- **Error tracking**: GlitchTip/Sentry-compatible DSN env (optional) wired in
  all 4 surfaces; frontend ErrorBoundary posts to `/api/client-errors`
  (ring-buffered in Postgres) so we capture tab crashes inside Teams, where
  the client can't open devtools.
- **Debug bundle**: `GET /internal/debug-bundle` (admin-key gated) → zip of:
  versions, container statuses, last 2h logs (from a ring buffer table),
  last 50 client errors, DB row counts, config checksums (values redacted),
  scheduler job states. Surfaced as a **System page** in admin with a
  download button — "send us this file" is the whole support flow.
- **Health that means something**: `/readyz` checks DB round-trip + (bot)
  Bot Framework token mint; compose healthchecks use it; System page shows
  green/red per dependency.
- Feature flags via env (`FEATURE_PHOTOS`, `FEATURE_COMMENTS`…) so a broken
  feature can be switched off remotely without a release.

Acceptance: fresh Ubuntu box → running product in <15 min with only
`install.sh`; a simulated bug is diagnosed from the debug bundle alone.

## Sequencing & effort

| Phase | What | Effort | Depends on |
|---|---|---|---|
| 0 | Architecture spine (identity, per-user data, authz, persistence) | ~1 wk | — |
| 1 | Feeds → Facebook standard | ~1.5 wk | 0 |
| 2 | Admin → better standard | ~1 wk | 0 (0.3 for login) |
| 3 | Employee app personal truth | ~0.5 wk | 0 |
| 4 | Distribution + debugging | ~1 wk | parallel-safe with 1–3 |

Total ≈ 5 weeks single-threaded; Phases 1/2/3 are parallelizable after 0.

## What stays as-is (deliberately)
- Bot conversation flows + adaptive cards (already the strongest part).
- Docker/compose local dev setup and Render Solos deployment.
- Teams manifest/SSO wiring (proven working; only URLs change per tenant).
- shadcn-based admin shell and the July quality pass (inline editor,
  broadcast composer, users roster) — Phase 2 builds on it, not over it.
